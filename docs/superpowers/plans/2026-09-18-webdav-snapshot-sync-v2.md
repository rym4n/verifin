# WebDAV JSON Snapshot Sync v2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the current per-entity WebDAV v1 upload/scan path with an immutable per-device JSON snapshot protocol that keeps local entity-level merge, conflicts, attachments, migration safety, and copyable diagnostics.

**Architecture:** Keep `SyncRepository`, `SyncProjection`, `SyncLedgerReducer`, SQLite remote-apply transactions, and `SyncCoordinator` as the domain boundaries. Add v2 snapshot value objects/codecs and a root-only WebDAV transport, then route `SyncEngine` through v2 while retaining the v1 reader as a read-only migration/bridge. Persist snapshot publications, cursors, and verified attachment hash mappings in SQLite so crash recovery and cross-restart reuse are deterministic.

**Tech Stack:** Dart/Flutter, sqflite/sqflite_common_ffi, `crypto`, `cryptography`, `xml`, existing `SyncCodec`, `SyncProjection`, `SyncLedgerReducer`, and the existing real/stub WebDAV transports.

**Spec:** `docs/superpowers/specs/2026-09-18-webdav-snapshot-sync-v2-design.md`

## Global Constraints

- Use WebDAV only; no server-side service, account system, or realtime background guarantee.
- v2 files are immutable root-level `verifin-sync-v2-<deviceId>-<20位序号>-<UTC时间戳>-<完整SHA256>.json` and `verifin-sync-v2-blob-<完整SHA256>.blob`.
- Device IDs are exactly 32 lowercase hexadecimal characters; snapshot sequence is persistent and strictly increasing with gaps allowed.
- Full snapshot JSON is capped at 16 MiB plaintext and 24 MiB encrypted envelope; raw attachments remain capped at 25 MiB and are chunked through `SyncWireLimits`.
- `rawHash` identifies the original chunk; `fileHash` identifies final uploaded encrypted bytes. Persist and freeze `rawHash -> fileHash` mappings before snapshot PUT.
- Pull-before-push: root `PROPFIND` first, no v2 `MKCOL`, one snapshot GET per changed remote device plus missing blob GETs, and one snapshot PUT when local publication is needed.
- Local merge remains entity-level with version vectors, tombstones, canonical conflict IDs, and SQLite atomic apply; a snapshot never overwrites the entire local database.
- Failed list/download/merge/upload never advances the corresponding cursor or clears unrelated outbox rows. Publications use `prepared -> blobs_ready -> PUT -> published`.
- Existing v1 data is read-only migration input. First migration blocks for user confirmation, performs a final v1 scan before the first v2 PUT, and keeps a read-only v1 fingerprint bridge after cutover.
- Logs are structured and copyable but must not contain credentials, full URLs/paths, payloads, ciphertext, or full device IDs.
- New user-visible strings require both `lib/l10n/app_zh.arb` and `lib/l10n/app_en.arb`; generated localizations are regenerated by the repository workflow.
- Do not run local Android APK/AAB builds; use Flutter analysis/tests locally and GitHub CI for release artifacts.
